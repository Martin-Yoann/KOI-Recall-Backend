# 0001 — 申报先于处置（Claim before disposal）

**状态**：已决定（沿用现状）
**范围**：消费者处置（Page 4）与事故通知的受理时序
**相关**：P0-A 第一条；`claim-flow.ts` 的 Page 4 注释；`drizzle-case-service.ts` 的提交事务

---

## 决定

**处置任务在申报提交的同一事务内创建；Page 4 只出现在提交之后。**

消费者看到处置步骤的前提是：他先提交申报，服务端在那一刻为案件钉住一个获批的指引版本、
开出一个处置任务并生成凭证；凭证随确认邮件送达，Page 4 靠它打开。

## 为什么

两个东西都只有在"案件存在"之后才可能成立：

1. **指引版本必须钉住一个案件。** 处置任务的
   `instruction_version_id` 是外键，任务属于案件。提交前没有案件，就没有可钉的对象。
2. **凭证必须属于一个任务。** Page 4 用 `X-Disposal-Token`（令牌只存哈希）打开。
   令牌在任务创建时生成；提交前没有任务，也就没有凭证可发。

因此"提交前 Page 4"不是把界面往前挪一格，而是要**在案件存在之前渲染处置步骤**。
那意味着：内容在没有任何案件、没有任何资格确认的情况下被展示 —— 而指引版本的批准
**可能在消费者提交之前被撤回**。展示的就不是"当前获批的内容"，而是"某个时刻曾获批的内容"。

## 被否的方案

| 方案                                       | 否决理由                                                                                                                                                  |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 先把 Page 4 显示出来，提交后再补案件与任务 | 步骤会在批准可能已被撤回、资格从未确认的情况下展示。这与"客户端不得自行推导处置"是同一类问题的镜像：服务端成了展示的追认者，而不是决定者。                |
| 提交前先建一个"占位任务"，提交时再绑定     | 占位任务需要一个 `campaign_version_id` 与资格判定，而资格来自案件提交时选定的产品。它会把"是否适用"的判定拆到两个时刻，正是 P0-A 第三条要收敛的那种分叉。 |

## 接受的风险

**事故只在申报提交时才被公司知悉。** 一个已经受伤、正在填表但**没有提交**的消费者，
公司尚不知情；`incidents.company_obtained_at` 在提交事务内写入，且**只写一次**
（全仓库没有任何 `update(incidents)` 的写入路径）。

这不是实现疏漏，是这条时序决定的直接后果。它同时意味着：**如果合规认定"首次接触"（草稿、
未提交的表单）就构成安全通知，那么 `company_obtained_at` 的语义就是错的**，本决定必须重审。

## 补偿控制

1. **提交即受理，不等照片。** 事故通知的受理发生在提交事务内，与证据上传、人工审核
   完全无关 —— 照片审核慢不会推迟事故可见。
2. **自动暂停。** 只要 `incidentAnswer !== 'no'`，提交事务内自动为处置任务放置
   `incident_evidence_retention` 暂停（`placedByStaffUserId` 为 null，表示非人所为）。
3. **报告性审查立即建立且为 pending。** 提交事务内创建 `reportability_reviews` 行，
   状态 `pending`，使案件进入合规阶段。
4. **结案被审查门禁挡住。** `closed` 在该审查缺失或仍为 `pending` 时被拒，
   **ADMIN 强制结案同样失败**（门禁写在 bypass 分支之外）。
5. **暂停与审查解耦。** 解除暂停需要人来操作并写明理由；审查结论本身不解除暂停，
   也不成为自动阻断的依据。

## 重审触发条件

以下任一成立时，本决定需要重审，而不是继续按它推理：

- 合规认定草稿（未提交的表单）构成公司收到安全通知 → 需要草稿层的首次获知时间（见计划 P1-A 的 C2）。
- 出现"消费者在提交前就已被指示不要使用产品"的实际需要 → 需要一条**不依赖案件**的
  停止使用提示路径，且它必须只展示经批准的停止使用与支持提示，不得展示处置步骤。
- 事故受理时限有监管口径（例如"知悉后 N 日"）而"知悉"被定义为首次接触。
